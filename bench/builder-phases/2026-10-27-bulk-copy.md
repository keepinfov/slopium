# Bulk-copy comparison — 2026-10-27

Issue #154 retains the existing word-sized buffer and direct path for pieces
of at most eight bytes. Long pieces are widened into a prepared tail by one
runtime call. This is the minimum throughput step, and does not resolve #144's
storage cost. The original kernels remain unchanged.

## Method and identity

Run [the paired comparison](README.md#paired-revision-comparisons) twice with
CPU 2, after all checks and builds finish. Each execution has two independently
warmed rounds: three warmups and fifteen samples, with seeds 154 and 155.
Within each workload the two Slopium revisions and C/Rust controls are shuffled.
The complete matrix covers 16 workloads and validates all 3840 measured
invocations against independent byte-count/checksum expectations. All warmups
are checked too. The host is carbon, Intel Core Ultra 7 265H, native x86-64
Linux; GCC 15.3.0, Rust 1.97.0 and Python 3.14.6. Slopium uses
`--optimize --strip`, C `-O2`, Rust `-O`.

Baseline: `2cf4cd2`, including the closure correctness fix. Candidate:
`bbac242` with current main integrated as `eb3aaba`; the remaining edits are
measurement tools/documentation. Both compiler binaries and library/runtime
identities stay unchanged throughout all comparisons. No production optimizer
or representation change is included.

## Short-write investigation

Fresh-process small cases fluctuate enough to require follow-up rather than a
blanket three-percent guarantee. In the first execution, the 512 KiB/five-byte
case had paired median changes +5.4% and +4.7%; the complete repeat changed
those paired medians to -0.4% and +1.0%. A 1000-record diagnostic also fluctuated
strongly, so a separate steady-state comparison tested all three noisy cases.

Use the same paired command with `--repeat-document 100` and repeated `--case`
arguments for `records-1000`, `pieces-8192-5` and `pieces-524288-5`. Each process
constructs/finalizes/checks 100 documents, prints and validates every result,
then the runner averages internal intervals after discarding the first five
documents. This yields thirty process samples per implementation, in two
rounds; document intervals are not treated as independent samples. C/Rust
controls use the same repetition. The original kernels are never wrapped.

| Workload | Round 1 append change | Round 2 append change |
| --- | ---: | ---: |
| records-1000 | +1.9% | -2.8% |
| pieces-8192-5 | +0.1% | +1.6% |
| pieces-524288-5 | -0.7% | -0.2% |

This follow-up does not reproduce a sustained short-write regression above
three percent. It does not establish a universal bound under fresh-process
scheduling and frequency variation. Steady-state wall/RSS measurements include
repeated lifetimes and must not replace the original control's wall/RSS figures.

## Validation and next work

The production change passed all stages of
`SLOPIUM_STRICT=1 scripts/verify.sh`, including Nix, with
no skips. The host adaptation supplies missing `/bin` fixture commands in a
private mount namespace, drops capabilities, and gives Nix the identical
source-only snapshot with binary substitution disabled. Registry/consumer
regeneration is byte-identical. Main and builder tests pass on both targets
in dev/release; direct C ABI bounds cases pass native ASan and AArch64.
The additional steady-state runner mode is checked by executing all selected
workloads against both revisions and both controls; normal mode is smoke-checked
again after adding that mode. Timing thresholds remain outside correctness CI.

The minimum step helps long pieces, while the original workload and memory gap
remain. Keep #144 open. #155's temporary digit list remains the next throughput
target selected by the phase baseline; #157's storage alternatives still need
separate design approval. Recheck the earlier numerical targets after those
changes, and keep small-case uncertainty visible.
