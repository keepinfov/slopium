# Compact builder storage — 2026-10-28

Issue #157 compares a runnable Slopium packed-word prototype with the current
builder and three explicitly separate native C storage models. The resulting
[proposal](proposal.md) recommends builder-local word packing for separate
approval. `D-165` remains deferred; no production representation, compiler,
installed runtime symbol, ordinary collection or release version changes.

## Capacity and RSS

Capacity includes geometric reserve and, for packed words, an eight-byte scalar
partial-word cache. It excludes allocator overhead and the remaining
descriptors. Current Slopium List capacity is calculated from its frozen
four-element initial reserve/doubling rule; packed capacity uses full-word count
`floor(logical_bytes / 8)`. Native capacity is printed by each executable and
checked against that rule on every sample. RSS values below are identical
medians in both rounds; they measure the full process, including final copy.

Useful packed storage is one byte per logical byte plus at most eight bytes of
padding/cache, before documented spare capacity. At the original size, reserve
drops from 8388608 to 1048584 bytes. Native owner/narrow reserve is 1048576
bytes there, omitting the eight-byte word cache. Small RSS rows reach the
process floor and do not establish equal owner metadata costs.

The Slopium prototype has a 24-byte struct payload plus the ordinary 48-byte
List header, versus 8 + 48 bytes for the current builder on these 64-bit
targets. Its tail is already counted in capacity above; do not count it twice.
The C models deliberately share a 64-byte descriptor containing generic-list
callback slots, a tail and length; none is a minimal production owner layout.
Callbacks are null and only primitive elements are supported.

The largest packed 4 MiB-piece RSS is **9904 KiB**, below the 16384 KiB goal in
both rounds for all three piece widths. Five-byte rows contain the largest whole
number of pieces (4194300 bytes), not a rounded-up document. All finalizations
copy; zero-copy transfer is not measured.

Every append row improves in both rounds, including five-byte pieces. Every
indexed-read row is slower in both rounds: selection of a full word or tail,
bounds and shift/mask replace the old direct word element access. This is a real
tradeoff, not a claim that all operations become faster. Today Builder exposes
its raw list but no public logical `read-at`; callers that use that field
nevertheless need an explicit migration and cost disclosure.

Finalization regressions above 3% repeat for 50000 short integers and all 8 KiB
piece rows. The bridge selects/decodes words per byte, while current
`sl_rt_string_from_bytes` masks each already separate word. The C word model
also repeatedly finalizes more slowly than byte models. These comparisons
support a decoding cost; they do not isolate exact guard/shift/cache shares.
Large-buffer finalization is faster as the 8× larger source is avoided. The
regressions remain reported and must be revisited in production #160. No
original-control speedup is reconstructed by adding diagnostic medians.

primitive stride but retains generic per-element push across a translation-unit

The owner model wins bulk-piece copying, reads and finalization, but not every
integer/record append. Merely narrowing a generic list retains push cost and

solely to meet the builder goals, which actual local packing meets.

## Validation and remaining production work

The complete corrected `SLOPIUM_STRICT=1 scripts/verify.sh` passed, including
all cross/object, runtime memory tools, Neovim and Nix checks; no skips. The
NixOS host adaptation supplies `/bin/sh`, `true`, `false`, `echo` in a private
user/mount namespace and drops capabilities before the suite. The flake check
receives a clean copy of the same tracked and new nonignored sources, avoiding
ignored build output; source contents are not altered.

The corrected `check.sh` passed native/AArch64 dev/release, core-only linkage on
both targets/profiles, native Memcheck and ASan/UBSan, empty/partial/growth,
clone/abandon/drop, all eight offsets, NUL/high bytes/UTF-8, integer limits,
bounds and malformed C-bridge arguments. The freestanding bridge object depends
only on allocator and panic hooks. An additional loan probe produces `SL0300`;
public-field and mutable-String probes are reproduced in the proposal.

Review corrected an inconsistent research String `cap`: allocation already
included NUL, but the header omitted it. Empty/nonempty header assertions now
require `cap = len + 1`, matching runtime. The full gate and complete paired
matrix were rerun after the correction. The earlier matrix is superseded and
supplies none of the tables above.

This research prototype is not production integration: it has a separate
benchmark-local type, does not prove `core:float` integration, and does not
check every forged public struct state at every language entry. The proposal
requires explicit invariant checks, overflow behavior, cache/interface and
library checksum updates, both backend/profile fixtures and remeasurement in
#158–#160. It preserves today’s compiler and ordinary list/slice ABI.

The prototype pre-fills one ordinary list element per completed word. It
therefore does not meet #159's stronger one-capacity-decision-per-piece item.
The proposal explicitly requests accepting measured word-prefill initially and
deferring a compiler reserve/header-FFI feature. No acceptance item is silently
waived and no new reserve builtin is implemented. Approval must cover that scope
adjustment as well as the representation and compatibility policy.

All timings are native x86-64. AArch64 execution under QEMU verifies functional
behavior and core linkage, not target throughput. The separate mutable-field
probe also passed both targets/profiles; direct `replace`/`push` clients need
migration beyond changing the field name.

The recommended default Builder field replacement is a breaking change. Approval
must explicitly cover the packed-word representation and direct-field migration
before a tracked decision supersedes `D-165` or production starts. A separate
opt-in type/module would be a different public API decision and would leave
existing callers on the large builder. #157 stays open at this approval gate;
#158–#160 remain blocked. Projects are untouched.
